# TelegramMCP

[English](../../README.md) · **Русский**

Самостоятельно размещаемый MCP-сервис для чтения и отправки сообщений через ваш аккаунт Telegram. Личные чаты, группы и каналы используют одни и те же инструменты и идентификаторы диалогов. Telegram по-прежнему применяет права аккаунта: подписка на канал не даёт права публиковать в нём.

## Модель развёртывания

Один Docker-образ предоставляет один Streamable HTTP MCP API по пути `/mcp`:

| Развёртывание | Подключение |
| --- | --- |
| Локальный Docker-сервис | Агент подключается к `http://127.0.0.1:8000/mcp`. Compose публикует порт только на loopback. |
| Docker-сервис на сервере | Совместимый удалённый клиент подключается через HTTPS reverse proxy с bearer-аутентификацией. |

Пользователи управляют собственными развёртываниями; централизованно размещённый сервис не нужен. Каждое развёртывание использует один аккаунт Telegram и одну постоянную сессию. Одновременно с этой сессией запускайте только один сервис или одну операторскую команду.

Серверный режим сейчас поддерживает статический bearer-токен. OAuth и опубликованный плагин ChatGPT пока не реализованы. Браузерной или облачной интеграции, требующей OAuth, нужна эта дополнительная реализация; одно лишь развёртывание этой версии на VPS не делает её совместимой с любым хостом плагинов.

## Быстрый старт в Docker

Установите Docker с Compose. В WSL включите интеграцию Docker Desktop для своего дистрибутива.

1. В пустом каталоге скачайте файл Compose и пример конфигурации, затем задайте в `.env` значения `TELEGRAM_API_ID` и `TELEGRAM_API_HASH` из [настроек приложения Telegram](https://my.telegram.org/apps):

   ```bash
   curl -fsSL -o compose.yaml https://raw.githubusercontent.com/Duby67/TelegramMCP/main/compose.yaml
   curl -fsSL -o .env https://raw.githubusercontent.com/Duby67/TelegramMCP/main/.env.example
   ```

2. Загрузите опубликованный образ и войдите в аккаунт интерактивно:

   ```bash
   docker compose pull
   docker compose run --rm telegram-mcp auth
   ```

   Введите номер телефона, код входа и пароль 2FA, если он запрошен. Код и пароль вводятся в скрытых запросах терминала. Вход — операторская команда, она никогда не доступна агенту.

3. Запустите сервис:

   ```bash
   docker compose up -d
   curl http://127.0.0.1:8000/health
   ```

   После запуска эндпоинт здоровья возвращает `{"status":"ok"}`. Это проверка живости процесса, а не живая проверка связи с Telegram.

4. Подключите агента и попросите показать ваши чаты и каналы. Список содержит только метаданные; чтение истории и отправка сообщений изначально запрещены. Попросите агента поработать с выбранным диалогом и подтвердите право чтения или отправки в интерфейсе вашего MCP-клиента. Копировать идентификаторы в `.env` не требуется.

Compose хранит сессию и `permissions.sqlite` в именованном томе `telegram-session` и запускает контейнер с UID 10001 и корневой файловой системой только для чтения. Обычные перезапуски и обновления образа сохраняют сессию и подтверждённые разрешения. `docker compose down -v` удаляет оба хранилища и требует нового входа и новых разрешений.

Перед очередной командой `auth` или `dialogs` остановите работающий сервис:

```bash
docker compose stop telegram-mcp
docker compose run --rm telegram-mcp dialogs
docker compose up -d
```

После изменения `.env` выполните `docker compose up -d`, чтобы пересоздать сервис с новой конфигурацией; простой перезапуск не перечитывает окружение.

## Подключение агента

Выберите Streamable HTTP и укажите `http://127.0.0.1:8000/mcp`. Транспорт STDIO сервис не предоставляет. Для запросов подтверждения используются MCP-сессии с состоянием и ответы SSE; reverse proxy должен поддерживать потоковую передачу и сохранять `Mcp-Session-Id`.

MCP-хост должен поддерживать form elicitation и показывать запросы разрешений пользователю. Если подтверждение не поддерживается, отклонено, отменено или завершилось ошибкой, разрешение не выдаётся. Сервер доверяет ответу хоста: используйте клиент, который требует ответа человека и не поручает модели автоматически отвечать на elicitation. Фраза «пользователь разрешил» в обычном аргументе инструмента не выдаёт доступ.

Для совместимого клиента с конфигурацией MCP-серверов задайте URL сервера и, если настроен, bearer-токен. Например, `config.toml` в Codex может содержать:

```toml
[mcp_servers.telegram]
url = "http://127.0.0.1:8000/mcp"
# Add this when MCP_TOKEN is configured; set the same token in the client environment.
# bearer_token_env_var = "TELEGRAM_MCP_CLIENT_TOKEN"
```

Агенты внутри другого контейнера не могут напрямую использовать адрес `127.0.0.1` хоста. Подключайте их через явно настроенную приватную Docker-сеть, требуйте токен и добавьте имя хоста сервиса в `MCP_ALLOWED_HOSTS`.

## Развёртывание на сервере

Используйте на сервере тот же образ и тот же файл Compose:

- Задайте `MCP_MODE=server` и `MCP_TOKEN` — случайный токен длиной не менее 32 символов.
- Добавьте публичное имя хоста в `MCP_ALLOWED_HOSTS`, сохранив при необходимости локальные записи. Например, допишите `mcp.example.com,mcp.example.com:*`, заменив пример на свой домен.
- Оставьте опубликованный порт Docker на `127.0.0.1`; HTTPS завершайте на reverse proxy на хосте.

[deploy/Caddyfile](../../deploy/Caddyfile) — стартовая конфигурация для Caddy, работающего на хосте. Замените в нём имя хоста, направьте DNS на сервер и настройте Caddy отдельно. Клиенты используют `https://YOUR_HOST/mcp` и заголовок `Authorization: Bearer YOUR_TOKEN`. Прокси должен сохранять этот заголовок. Приложение не доверяет пересылаемым заголовкам и само не предоставляет TLS.

Заголовки Origin из браузера по умолчанию отклоняются. Сервис рассчитан на MCP-хосты, выполняющие запросы между серверами; CORS для прямого JavaScript в браузере не включён. Список разрешённых Origin не добавляет поддержку OAuth или CORS.

## Инструменты

Все инструменты возвращают JSON и в текстовом содержимом MCP, и в структурированном содержимом. Идентификаторы диалогов — канонические десятичные строки со знаком, чтобы клиенты на JavaScript не теряли точность целых чисел. Получайте их из `list_dialogs` или операторской команды; названия и имена пользователей в качестве идентификаторов не принимаются.

| Инструмент | Параметры | Результат |
| --- | --- | --- |
| `list_dialogs` | `limit` (1–100, по умолчанию 50), необязательный `cursor` | Метаданные всех диалогов: тип, текущие права чтения/отправки, подсказка Telegram о возможности отправки и `next_cursor`; без содержимого сообщений. |
| `request_dialog_access` | `dialog_id`, `access` (`read` или `write`) | Запрашивает подтверждение пользователя и возвращает `granted`, `already_granted`, `denied` или `cancelled`. |
| `revoke_dialog_access` | `dialog_id`, `access` (`read` или `write`) | Немедленно отзывает указанное право, оставляя другое без изменений. |
| `get_messages` | `dialog_id`, `limit`, необязательные `before_id`, `since`, `until` | Сообщения от новых к старым и `next_before_id`. |
| `send_message` | `dialog_id`, `text`, необязательный `reply_to_message_id` | `status: "sent"` и отправленное сообщение. |

Страницы диалогов сортируются по числовому идентификатору; передавайте `next_cursor` в следующий вызов. Перед пагинацией перебираются все диалоги аккаунта, поэтому на больших аккаунтах это может занять больше времени. Изменения членства между вызовами могут изменить доступные результаты.

Права чтения и отправки независимы, относятся к одному диалогу и сохраняются до отзыва. Право отправки разрешает последующие отправки, а не только одно сообщение. Разрешения действуют для всех аутентифицированных клиентов этого развёртывания с одним аккаунтом. На подтверждение отводится пять минут. Выдача и отзыв прав применяются без перезапуска контейнера. Команда `telegram-mcp dialogs` остаётся необязательной диагностикой для владельца, а не обязательным этапом настройки.

Для истории передавайте `next_before_id` как `before_id`. `before_id` исключается, `since` включается, `until` исключается. Фильтры времени должны содержать часовой пояс, например `2026-01-01T09:00:00+03:00`. Каждое сообщение содержит идентификатор, время, доступный идентификатор отправителя, текст, цель ответа и признак наличия медиа; медиафайлы не скачиваются.

Отправка принимает непустой простой текст длиной до 4096 кодовых единиц UTF-16. Форматирование Markdown и предпросмотр ссылок отключены. Сообщение, на которое отвечают, должно существовать в том же диалоге. Локальное право записи не отменяет ограничений Telegram; метаданные о возможностях — лишь подсказка, окончательное решение принимает Telegram.

Ошибки операций Telegram и доступа выставляют в MCP `isError: true` и возвращают объект `error` с `code`, `message`, необязательным `retry_after_seconds` и необязательным `delivery_status`. Некорректные аргументы инструмента также могут приводить к ошибкам валидации SDK с `isError: true`.

Значения статуса доставки:

- `not_attempted`: отправка заблокирована или завершилась ошибкой до вызова отправки.
- `rejected`: Telegram явно отклонил отправку, в том числе из-за ограничения частоты.
- `unknown`: отправка могла пройти, но подтверждение потеряно. Прежде чем решать, отправлять ли повторно, проверьте чат в Telegram.

Сервис отключает в Telethon автоматические повторы запросов и автоматическое ожидание при flood wait. У операций Telegram срок 30 секунд; у предварительной проверки отправки и у самой отправки свои сроки. Неудачная отправка никогда не повторяется автоматически. Отдельные вызовы инструментов от клиента не дедуплицируются, поэтому клиенты не должны вслепую повторять `send_message`.

## Конфигурация и данные аккаунта

| Переменная окружения | Назначение / значение по умолчанию |
| --- | --- |
| `TELEGRAM_API_ID`, `TELEGRAM_API_HASH` | Обязательные учётные данные приложения Telegram. |
| `TELEGRAM_SESSION_DIR` | Хранилище сессии; `./data` при нативном запуске, `/data` в Compose. |
| `MCP_MODE` | `local` (по умолчанию) или `server`. |
| `MCP_TOKEN` | Необязателен локально, обязателен в серверном режиме; не менее 32 символов. |
| `MCP_HOST`, `MCP_PORT` | Нативный адрес привязки `127.0.0.1:8000`; в Compose внутри контейнера привязка к `0.0.0.0:8000`. |
| `MCP_ALLOWED_HOSTS` | Явный список разрешённых Host; по умолчанию localhost и loopback с портами и без. Одиночный `*` отклоняется. |
| `MCP_ALLOWED_ORIGINS` | Точные origin через запятую; пустое значение отклоняет запросы с заголовком Origin. |

`.env.example` содержит одинаковый набор настроек для локального и серверного запуска: учётные данные Telegram, `MCP_MODE`, `MCP_TOKEN` и `MCP_ALLOWED_HOSTS`. Остальные настройки из таблицы необязательны. Непустые устаревшие `TELEGRAM_READ_DIALOG_IDS` или `TELEGRAM_WRITE_DIALOG_IDS` вызывают понятную ошибку конфигурации вместо выдачи доступа; удалите их и используйте подтверждение пользователя.

Учётные данные Telegram берутся из окружения. Сессии аккаунта и хранилище разрешений остаются в томе пользователя; значения учётных данных и необработанные исключения Telegram не попадают в результаты инструментов. Приложения с доступом к окружению или тому всё равно могут прочитать секреты или изменить права. Не помещайте `.env`, файлы сессий и `permissions.sqlite` в систему контроля версий и в резервные копии, предназначенные для передачи другим. Запрошенные сообщения передаются модели для обработки.

## Разработка и проверка

Установите [uv](https://docs.astral.sh/uv/), затем:

```bash
uv sync --locked --python 3.12
uv run --env-file .env telegram-mcp auth
uv run --env-file .env telegram-mcp dialogs
uv run --env-file .env telegram-mcp serve
```

Чтобы проверить локальный образ через Compose, соберите его под опубликованным именем: `docker build -t ghcr.io/duby67/telegrammcp:latest .`; `docker compose pull` заменит его опубликованным образом. Пуш тега `vX.Y.Z` публикует `X.Y.Z`, `X.Y` и `latest` для amd64 и arm64.

Выполняйте операторские команды до запуска `serve`. Нативная блокировка сессии требует Unix-подобного окружения; на Windows поддерживается запуск через Docker. Приложение использует API MCP SDK 1.x, зависимости закреплены в `uv.lock`.

```bash
uv run pytest -q
uv run ruff check --select E,W,F,B,I,UP,SIM,FURB,PLW1510,RUF100 --line-length 100 src tests
uv run ruff format --line-length 100 --check src tests
uv run mypy --check-untyped-defs --ignore-missing-imports --warn-redundant-casts --warn-unused-ignores src
git diff --check
```

Тесты используют поддельный клиент Telegram, включая полный обмен через настоящие клиент и сервер MCP SDK. Они никогда не входят в Telegram и не отправляют настоящих сообщений. CI также собирает Docker-образ. Приёмочную проверку на реальном аккаунте нужно выполнять отдельно, с явно выбранным тестовым диалогом: получить его в списке, прочитать историю, отправить сообщение, перезапустить сервис и убедиться, что сохранённая сессия по-прежнему работает.

Дайджесты по расписанию, поиск, OAuth, передача файлов, редактирование сообщений и реакции не входят в эту первую версию. Расписание — задача подключённого клиента или отдельного планировщика; во время выполнения задачи этот сервис должен быть запущен и доступен.
